# Job Seeker Copilot v1.1 release plan

Status: **planning and non-production implementation**

Target release owners: Bernard and Danny, as Job Seeker Copilot partners

Access status: the generic personal-account owner is verified; Danny's exact
GitHub username and repository/Project CRUD access are not yet verified.

Production safety: this plan does not authorise a production deployment,
repository transfer, DNS change, Amplify change, Pages change, secret rotation,
or whole-fleet restart.

## Release intent

v1.1 is a focused stability and operating release driven by public use. It is
represented by `Release = v1.1` in the existing
[Product Development Project](https://github.com/users/jobseekercopilot/projects/1),
not by an Epic, milestone, tag or GitHub Release. Existing Product history
remains in that Project; work is classified and linked rather than recreated.

The release has four Features:

1. [**Public Tester Feedback & Issue Reporting**](https://github.com/jobseekercopilot/infrastructure/issues/303)
2. [**Public Tester Bug Fixes**](https://github.com/jobseekercopilot/infrastructure/issues/304)
3. [**Deploy Individual Services Without Restarting the Entire Application**](https://github.com/jobseekercopilot/infrastructure/issues/305)
4. [**Promotion & Public Testing — Danny**](https://github.com/jobseekercopilot/infrastructure/issues/306)

Stories, Research and Bugs sit beneath the relevant Feature using the Project's
existing child-work convention. There is no v1.1 Epic layer.

## Goals

### Learn from real users

Give testers a simple, non-technical route for reporting breakage, confusion and
ideas, and turn those reports into structured evidence.

### Make reporting safe and easy

The in-product flow must explain the diagnostic data it sends. It must not send
passwords, tokens, cookies, payment data, full CVs, cover letters, or application
content. GitHub credentials must never enter browser code.

### Fix user-discovered problems

Public feedback should progress through triage, reproduction, priority, fix,
regression test, PR, release and post-release verification, while retaining its
source and related evidence.

### Make updates faster

An eligible service change should build, test, publish and replace only that
service. Unchanged healthy services should remain running. Failed replacement
must restore the previous immutable version and repeat health and smoke checks.

### Give promotion a proper home

Danny has a dedicated Promotion Feature and view for tester recruitment,
messages, assets, demos, outreach, feedback and release announcements. This is
an ownership focus, not an access restriction.

### Support the partnership

Bernard and Danny should both be able to manage repositories, issues, the Product
Development Project and normal development work. Production secrets and
protected-environment approvals remain separately safeguarded.

### Improve GitHub without risking the product

Make the repositories and Project easier to navigate, share and operate while
preserving issue numbers, comments, PR relationships, releases and closed work.

### Protect the live product

No GitHub cleanup or v1.1 experiment justifies downtime. Production deployment,
DNS, Pages, Amplify, AWS, packages, secrets and repository ownership remain
unchanged unless separately authorised and conclusively proven safe.

## Non-goals

- A broad product-feature release.
- Moving unrelated backlog work into v1.1.
- A repository transfer during this work.
- Renaming the current GitHub account or repositories.
- Weakening protected environments or exposing production secrets.
- Experimenting on the live application.
- Claiming zero-downtime replacement of the changed service before capacity and
  deployment-policy evidence supports it.

Unrelated ideas remain `Post-v1.1`, `Future` or `Backlog` and are captured under
`[Epic] Product Backlog and Continuous Improvements` when they meet the standing
evidence threshold.

## Feature 1: Public Tester Feedback & Issue Reporting

Feature: [Infrastructure #303](https://github.com/jobseekercopilot/infrastructure/issues/303)

Status: intake/store/client implementation is tested on feature branches and
disabled by default; it is not deployed or enabled.

### Intended outcome

An unobtrusive **Send feedback** action lets a tester select `Something is
broken`, `Something is confusing`, `Feature suggestion`, or `Other feedback`,
then supply a short title, description and optional reproduction steps.

Only an application route without query/fragment, a server-configured but
untrusted client-reported build hint, a server timestamp and explicitly opted-in
coarse browser/device diagnostics may be attached. Screenshots are deferred
until storage, redaction, malware handling, retention and deletion controls are
approved.

### Architecture gates

- Browser input is strictly schema-, size- and enum-validated.
- Mutations require the established session/CSRF boundary when the chosen route
  is authenticated; an anonymous route needs equivalent edge abuse controls.
- Rate limiting, bounded timeouts, neutral errors, sanitisation and content-free
  operational logs are mandatory.
- A GitHub integration, if selected, runs only in a server-side component with a
  credential scoped to one private issue repository. The issue bridge must not
  live in browser code.
- A safer feedback store with partner triage is preferred if direct issue
  creation cannot meet the credential, privacy, spam and availability gates.

### Initial child work

- [Research: select and threat-model the feedback ingestion and Project-routing
  architecture](https://github.com/jobseekercopilot/infrastructure/issues/307).
- [Story: implement accessible feedback UX and explicit diagnostic consent](https://github.com/jobseekercopilot/job-seeker-copilot-client/issues/143).
- [Story: implement validated ingestion, abuse controls, safe storage/routing and
  user confirmation](https://github.com/jobseekercopilot/job-seeker-copilot-landing/issues/73).
- [Story: automate privacy, security, accessibility and submission tests](https://github.com/jobseekercopilot/e2e/issues/62).

All four are native children of Feature #303. The chosen design is a dedicated,
retained and encrypted feedback store plus an authenticated partner-operated
dry-run/apply triage CLI; browser code contains no AWS or GitHub credential.
See the [feedback triage runbook](../public-testing/feedback-triage.md).

## Feature 2: Public Tester Bug Fixes

Feature: [Infrastructure #304](https://github.com/jobseekercopilot/infrastructure/issues/304)

Initial child: [establish public-tester Bug triage and release evidence](https://github.com/jobseekercopilot/infrastructure/issues/308).
No speculative Bug was created before a real tester defect was reproduced.

### Triage flow

```text
Public report -> Triage -> Reproduce -> Prioritise -> Fix -> Test
              -> PR -> Review -> Release -> Verify
```

Each Bug should retain, where applicable:

- originating feedback reference;
- `Source = Public Tester`;
- affected area and version/build;
- reproduction evidence and severity;
- parent v1.1 Feature;
- fixing PR and regression test; and
- release and post-release verification.

The target partner model lets either partner create, edit, prioritise, assign,
link, close, reopen and retarget the work. Danny's current access remains
unverified. Existing matching Bugs are reused rather than duplicated.

## Feature 3: independent service deployment

Feature: [Infrastructure #305](https://github.com/jobseekercopilot/infrastructure/issues/305)

The current AWS topology already has one digest-pinned ECR image, ECS task
definition, ECS service and Cloud Map identity per application service. The
whole-fleet interruption is imposed by the full-release procedure and its global
attestation, not by ECS itself.

The v1.1 implementation begins with a production-disabled pilot that proves:

```text
eligible service + immutable version
  -> build/test/scan
  -> exact one-service plan
  -> replace only selected service
  -> readiness + caller smoke
  -> unchanged-service assertion
  -> deployment record
```

Failure must select the captured prior immutable version, replace the same
service, repeat readiness/caller smoke, and record the rollback. The initial
pilot excludes edge, database-owning, recovery-critical and evidence-pinned
services. Production enablement requires its own reviewed maintenance task.

Native child work:

- [Research: establish current deployment coupling and service eligibility](https://github.com/jobseekercopilot/infrastructure/issues/316) — architecture audited.
- [Story: safe non-production single-service deploy and rollback operator](https://github.com/jobseekercopilot/infrastructure/issues/312) — implemented and unit-tested.
- [Story: production-compatible service patch manifest and plan-only workflow](https://github.com/jobseekercopilot/infrastructure/issues/309) — planned; production path remains disabled.

The evidence and operator contract are in
[ADR 0004](../adr/0004-independent-service-deployment-pilot.md) and the
[pilot runbook](../independent-service-pilot-runbook.md). The local pilot may
briefly interrupt only the selected service; it does not claim zero downtime for
that service or production eligibility.

## Release readiness

Use the [v1.1 Board](https://github.com/users/jobseekercopilot/projects/1/views/8),
[v1.1 Roadmap](https://github.com/users/jobseekercopilot/projects/1/views/15)
and [Release Readiness view](https://github.com/users/jobseekercopilot/projects/1/views/13).

v1.1 may be considered ready only when:

- the four Features and their necessary child work are correctly classified;
- public feedback has a usable, privacy-reviewed ingestion and triage route;
- v1.1 public-tester Bugs have clear priority, ownership and regression evidence;
- independent deployment and rollback pass outside production;
- unchanged-service continuity and health evidence is retained;
- partner access limitations are either removed or explicitly accepted with an
  organisation-migration task;
- CI and relevant security/accessibility checks pass on reviewed PRs;
- release notes identify exact service versions and database/contract
  compatibility; and
- a separately approved production change and rollback window exists.

## Production invariants

Throughout v1.1 development:

- production remains running;
- Project/issue work cannot trigger deployment;
- unfinished v1.1 code does not merge to the live release branch;
- DNS, Pages, Amplify, AWS, secrets and package locations remain unchanged
  unless a separately reviewed change proves safety; and
- uncertain production impact results in documented future work, not an
  experiment.
