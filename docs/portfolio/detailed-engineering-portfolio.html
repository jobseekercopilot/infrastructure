Executive overview

One workspace for the fragmented work of finding a job

Job Seeker Copilot helps a candidate organise career evidence, discover vacancies, prepare grounded documents, track applications and retain an auditable record of what was used.

It is not “AI writes a CV”. The product is a traceable workflow from verified career evidence and a real vacancy to an application-specific document set.

Candidate problem

Vacancies, versions, portals, evidence and follow-up are scattered across tools.

Product response

Structured profile, multi-provider discovery, document lineage and application tracking.

Engineering response

Owned domain state, provider gateways, versioned contracts and recoverable workflows.

Current boundary

Controlled private beta; local persistent operation, not public production.

Architecture principles

Decomposed by ownership, corrected by failure

One authoritative owner

Accounts, profile evidence, saved vacancies, applications, documents, wallet entries and operation checkpoints have explicit systems of record.

Gateways isolate trust

Browser, provider and model DTOs/credentials stop at controlled boundaries. Domain services consume canonical contracts.

Immutable references

Evidence snapshots, saved jobs, document versions and applied selections resist later mutation.

Failure is state

Retries, ambiguous outcomes and partial side effects are persisted and reconciled rather than hidden behind a generic error.

Evolution pattern

Original simplification

Generate content, save output and continue synchronously.

→

Current operation

Persist intent, snapshot inputs, reserve credit, checkpoint side effects, validate output, approve exact versions and reconcile application references.

Why microservices?

Different trust, state and failure boundaries—not repository count for its own sake.

Why contracts?

Independent repositories otherwise compile against yesterday’s assumptions.

Why fixtures?

Repeatable failure and zero-spend regression, kept distinct from live confidence.

Architecture was not fixed in advance. Document association, rich evidence, provider inconsistency and realistic concurrency each forced clearer ownership or recovery rules.

Profile and Evidence Library

Career history is structured product data

Synthetic fixture: progressive employment, projects, qualifications, skills and preferences.

Synthetic fixture: evidence entries expose category, confirmation, provenance and revision state.

Entry

Stable category and identity; visibility, lifecycle and review state.

Revision

Immutable facts, creator, confirmation and content digest.

Snapshot

Purpose, selected revisions, section order, profile revision and digest.

Why this exists. Repeatedly pasting a free-text biography into a model makes provenance and later correction impossible. Structured evidence allows a user to confirm facts once, select them for a purpose and retain exactly what supported a generated document.

Canonicalisation and deduplication

Heterogeneous adverts need explainable identity

Canonical fields retained

  • canonical job ID and provider/external IDs;
  • all source references and canonicalised URLs;
  • title, company, location and workplace type;
  • salary, posted/expiry dates and description;
  • specialist/apprenticeship details and provenance.

Duplicate signals

  • same canonical apply URL;
  • overlapping source/apply options;
  • normalised company + high title similarity;
  • normalised location + compatible dates;
  • compatible descriptions within configured thresholds.
if (sameCanonicalApplyUrl(left, right) || overlappingApplyOptions(left, right)) return 1.0;
if (sameCompany(left,right)
    && titleSimilarity(left,right) >= 0.90
    && sameLocation(left,right)
    && postedDatesCompatible(left,right)
    && descriptionsCompatible(left,right)) return 1.0;

mergeDuplicateJobs(primary, duplicate); // also merges every source reference

Naïve result

Two apparently identical cards or, worse, one merged record that loses the source needed to apply.

→

Current result

One canonical display record can retain multiple provider references, a preferred apply URL and field provenance.

Known boundary. Deduplication is deliberately rule-based and explainable. It can still miss semantically identical adverts or avoid merging uncertain ones; it is not an opaque similarity model.

Document architecture

A document is a family, immutable versions and files—not one mutable blob

Families expose type, job scope, source, retention, current state and application associations.

Document Store owns

  • family and immutable version records;
  • generated/uploaded source and lineage;
  • current/approved pointers;
  • DOCX/PDF metadata, checksum and MIME;
  • filesystem bytes locally or S3-compatible provider;
  • archive, restore, recoverable delete and tombstones.

Upload boundary

PDF/DOCX ≤10 MiB; bounded extraction; MIME/signature checks; isolated ClamAV scanning; no model or AI-credit call.

Recovery, retry and reconciliation

“Try again” is unsafe when money or side effects may already exist

Failure/stateMeaningSafe behaviour
DOWNSTREAM_RETRYABLEReplay-safe step failed before/after a known idempotent mutationResume bounded step with same key

Stable keys

Reservation, generation, storage, export and application side effects derive from one operation ID.

Retained response

A captured provider response can be re-parsed/revalidated without another paid call.

Leases/deadlines

Concurrent workers coalesce; persisted absolute deadlines prevent infinite recovery.

Wallet rule. Release only when model use is known not to have completed. Commit actual usage idempotently. An ordinary browser retry must never become a second user charge.
Safe recovery architecture23
Engineering case study · rich-profile CV

Realistic data broke assumptions that compact fixtures did not

1

Failure: a real rich profile produced exact duplicate structured CV content.

The model response was fluent, but strict validation correctly rejected the repeated structure.

2

Failure: a subsequent generation reached the previous output/deadline boundary.

The operation could not safely assume whether another paid request was appropriate.

3

Why confidence was overstated: compact deterministic personas exercised contracts but not realistic evidence volume, role ordering or output length.

Architecture response

  • purpose-appropriate CV output budget;
  • exact-duplicate structural repair;
  • re-run full claim validation after repair;
  • stronger vacancy/evidence selection and role prominence.
  • bounded safe LLM retry classification;
  • unknown-outcome reconciliation;
  • selected-output-aware recovery;
  • deterministic evidence-based CV fallback.

Old product outcome

Model rejection surfaced as a failed generation operation even when safe evidence existed.

→

Current product outcome

The model result may still be rejected, while the operation can complete with a grounded deterministic CV and the cover letter can remain the accepted model output.

Engineering lesson. Deterministic fixtures remain essential for regression, but representative rich profiles and paid/live boundaries are separate confidence layers.

Deterministic evidence-based fallback

Fail useful without pretending the model succeeded

/** Conservative CV from approved evidence only.
 * No semantic embellishment: canonical fields and narrative bullets
 * are copied from evidence; ordering uses lexical vacancy overlap. */
cv.targetRole = input.job.title;
addSkills(cv, rankedApprovedSkills.limit(12));
addEmployment(cv, approvedEmployment.limit(12));
addQualifications(cv, approvedQualifications.limit(8));
addProjects(cv, approvedProjects.limit(4));
notes.tailoringSummary = "evidence-based CV produced because model generation
did not yield an acceptable draft";

What fallback can do

  • copy canonical job/profile/evidence fields;
  • rank approved skills and evidence by lexical vacancy overlap;
  • preserve dates, organisations and fact provenance;
  • produce the same typed CV schema and claim ledger;
  • continue through Store, export and application workflows.

What fallback must not do

  • invent seniority, metrics or qualifications;
  • infer unstated technologies;
  • rewrite uncertain dates;
  • claim semantic understanding or model quality;
  • silently masquerade as AI-tailored output.
Product value. The operation remains useful even when the probabilistic collaborator is unavailable or unacceptable. Safety and completion are no longer identical to “the model returned JSON”.

Major defects and design gaps · I

Failures that changed ownership or workflow

1

Generated document not reliably associated with its application.

Found by realistic E2E. Generation linked selections before authoritative application identity/reconciliation was ready. The flow now creates/relinks the application and verifies exact references before selection; fixture and E2E preserve regression coverage.

2

Unsupported identity and claims could appear fluent.

Prompt-only trust was insufficient. Trusted identity moved outside the prompt; strict claim ledgers and evidence-path validation now reject unsupported specific claims.

3

Payment browser proxy routing could imply a capability that was not ready.

The BFF now fails closed for beta-disabled payment routes while backend wallet/fixture work remains testable and documented separately.

4

Capacity refresh destroyed the job card under interaction.

Playwright concurrency exposed unstable Angular tracking when canonical identity appeared after refresh. Stable provider-job identity changed 0/25 to 25/25.

5

Exact duplicate model structure caused full operation failure.

Narrow duplicate repair was added, followed by the same claim validation. Semantic rewrites remain forbidden.

6

Provider dates and offsets did not share one meaning.

Compatibility normalisation was added at provider/domain boundaries; open backlog items still guard offset preservation where contracts remain weaker.

Each fix added regression protection at the lowest useful layer and, where user behaviour mattered, at browser/E2E level.
Defect-driven engineering · 136
Major defects and design gaps · II

Failures that changed recovery, quality or boundaries

7

Rich-profile evidence was omitted or poorly prioritised.

Compact personas hid realistic selection pressure. Purpose-sized prompts, richer role/project evidence and deterministic relevance selection now preserve important software experience.

8

Model output budget and operation deadline disagreed.

A larger CV budget alone was not enough. LLM bounds, gateway read deadlines and durable absolute deadlines were aligned; ambiguous outcomes enter reconciliation rather than blind retry.

9

Selected-output recovery expected both documents.

After CV-only/letter-only selection shipped, recovery could misread missing unselected references. Operation state and client UI now report partial success truthfully.

10

Google location did not fit the direct postcode gateway design.

A Location Service was extracted; Google Maps Gateway now owns provider key/DTOs while canonical persistable fields stay provider-neutral.

11

Professional export work was stranded outside the integrated branch.

Git history located and reconciled template behaviour. Real rich-profile inspection then fixed A4 hierarchy, page breaks and pagination.

12

Contract/client drift recurred across independently versioned services.

Producer OpenAPI, reviewed revisions/checksums, generated clients and semantic policy gates replaced copied binaries and undocumented shape assumptions.

Maturity signal. The important result is not that defects existed; it is that realistic evidence identified why earlier tests missed them and converted them into architecture and regression controls.
