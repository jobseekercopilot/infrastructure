Executive overview

One workspace for the fragmented work of finding a job

Job Seeker Copilot helps a candidate organise career evidence, discover vacancies, prepare tailored documents, track applications and retain an auditable record of what was used.

The product is a connected workflow: structured evidence and a genuine vacancy become versioned, application-specific documents and an owned application record.

Candidate problem

Vacancies, versions, portals, evidence and follow-up are scattered across tools.

Product response

Structured profile, multi-provider discovery, document lineage and application tracking.

Engineering response

Owned domain state, provider gateways, versioned contracts and recoverable workflows.

Current boundary

Controlled private beta; local persistent operation, not public production.

Architecture principles

Decomposed by ownership, corrected by failure

One authoritative owner

Accounts, profile evidence, saved vacancies, applications, documents, wallet entries and operation checkpoints have explicit systems of record.

Gateways isolate trust

Browser, provider and model DTOs/credentials stop at controlled boundaries. Domain services consume canonical contracts.

Immutable references

Evidence snapshots, saved jobs, document versions and applied selections resist later mutation.

Failure is state

Retries, ambiguous outcomes and partial side effects are persisted and reconciled rather than hidden behind a generic error.

Evolution pattern

Original simplification

Generate content, save output and continue synchronously.

→

Current operation

Persist intent, snapshot inputs, reserve credit, checkpoint side effects, validate output, approve exact versions and reconcile application references.

Why microservices?

Different trust, state and failure boundaries—not repository count for its own sake.

Why contracts?

Independent repositories otherwise compile against yesterday’s assumptions.

Why fixtures?

Repeatable failure and zero-spend regression, kept distinct from live confidence.

Architecture was not fixed in advance. Document association, rich evidence, provider inconsistency and realistic concurrency each forced clearer ownership or recovery rules.

Fixture-mode gateways read governed provider/persona data. Live profiles replace only approved external boundaries while keeping application ownership unchanged.

Frontend and same-origin BFF

The Angular application is a product boundary, not a thin skin

Major user areas

  • Registration, sign-in, refresh and return

Engineering behaviour

  • Generated/typed API models where contracts exist
  • Same-origin Express route allowlist

Profile and Evidence Library

Career history is structured product data

Synthetic fixture: progressive employment, projects, qualifications, skills and preferences.

Synthetic fixture: evidence entries expose category, confirmation, provenance and revision state.

Entry

Stable category and identity; visibility, lifecycle and review state.

Revision

Immutable facts, creator, confirmation and content digest.

Snapshot

Purpose, selected revisions, section order, profile revision and digest.

Why this exists. Repeatedly pasting a free-text biography into a model makes provenance and later correction impossible. Structured evidence allows a user to confirm facts once, select them for a purpose and retain exactly what supported a generated document.

Selection becomes an immutable generation input

EvidenceSnapshot create(userId, request) {
  require(profile.revisionId && profile.contentDigest);
  for (entryId : request.entryIds) {
    revision = eligibleUserConfirmedRevision(entryId, userId);
    enforceSectionOrderAndFactLimit(revision);
    snapshot.addSelection(copyFactsAndDigests(revision));
  }
  snapshot.snapshotDigest = digest(snapshot);
  return repository.saveAndFlush(snapshot);
}

Canonicalisation and deduplication

Heterogeneous adverts need explainable identity

Canonical fields retained

  • canonical job ID and provider/external IDs;
  • all source references and canonicalised URLs;
  • title, company, location and workplace type;
  • salary, posted/expiry dates and description;
  • specialist/apprenticeship details and provenance.

Duplicate signals

  • same canonical apply URL;
  • overlapping source/apply options;
  • normalised company + high title similarity;
  • normalised location + compatible dates;
  • compatible descriptions within configured thresholds.
if (sameCanonicalApplyUrl(left, right) || overlappingApplyOptions(left, right)) return 1.0;
if (sameCompany(left,right)
    && titleSimilarity(left,right) >= 0.90
    && sameLocation(left,right)
    && postedDatesCompatible(left,right)
    && descriptionsCompatible(left,right)) return 1.0;

mergeDuplicateJobs(primary, duplicate); // also merges every source reference

Naïve result

Two apparently identical cards or, worse, one merged record that loses the source needed to apply.

→

Current result

One canonical display record can retain multiple provider references, a preferred apply URL and field provenance.

Known boundary. Deduplication is deliberately rule-based and explainable. It can still miss semantically identical adverts or avoid merging uncertain ones; it is not an opaque similarity model.

Document architecture

A document is a family, immutable versions and files—not one mutable blob

Families expose type, job scope, source, retention, current state and application associations.

Document Store owns

  • family and immutable version records;
  • generated/uploaded source and lineage;
  • current/approved pointers;
  • DOCX/PDF metadata, checksum and MIME;
  • filesystem bytes locally or S3-compatible provider;
  • archive, restore, recoverable delete and tombstones.

Upload boundary

PDF/DOCX ≤10 MiB; bounded extraction; MIME/signature checks; isolated ClamAV scanning; no model or AI-credit call.

Lifecycle actionMeaningWhat it does not do
Set currentSelect family recommendationDoes not rewrite an application
ApproveMake exact version eligibleDoes not auto-select it for a job
Archive/restoreReversible organisation stateDoes not mutate bytes
Delete/recoverRecovery-window lifecyclePurge remains separately controlled
Historical problem solved. Regenerating a CV tomorrow must not silently change the version associated with yesterday’s application.

Bounded request

The service sends the vacancy, ordered evidence, purpose and schema version—not unrestricted profile data. Trusted contact identity stays outside generated content.

Safe recovery

Exact duplicate structure may be repaired and revalidated. Classified retry is bounded; uncertain provider outcomes are reconciled before any new paid call.

Failure exposed by realistic use

A rich profile produced duplicate structure and then reached the previous output/deadline boundary—conditions compact fixtures had not represented.

→

General product correction

Budgets, repair, claim validation, selected-output recovery, outcome reconciliation and deterministic fallback now form one tested recovery policy.

Why this matters. The product can reject an unacceptable generated response without losing the user’s evidence selection, duplicating a wallet charge or pretending the response was valid.
Grounded content and safe recovery21
Document export

Structured content must still become a professional artifact

Privacy-safe synthetic persona; generated during the successful live-provider/OpenAI showcase. Real candidate documents are not retained in source control.

Typed render model

Sections, headings, roles, bullets, dates and contact fields are accepted as structured content—not executable or model-supplied HTML.

Editable and final formats

Apache POI builds DOCX and OpenPDF builds A4 PDF. Both are returned to Document Store with MIME type, size, checksum and stable export identity.

Visual controls

Heading hierarchy, compact spacing, keep-with-next, indentation, page breaks, headers and pagination are deterministic renderer concerns.

Replay safety

Repeating an export operation uses the exact source version and stable key; it does not silently create unrelated lineage.

Evidence of correction. Rich-profile inspection exposed weak hierarchy and page-flow regressions that compact fixtures did not show. The renderer and its visual regression checks were corrected as general product behaviour.

Why this starting point

  • Local Docker memory reached 8.64 GiB, while service CPU peaked near eight logical cores.
  • The 25-session run completed but had no useful deadline margin.

Major defects and design gaps · I

Failures that changed ownership or workflow

1

Generated document not reliably associated with its application.

Found by realistic E2E. Generation linked selections before authoritative application identity/reconciliation was ready. The flow now creates/relinks the application and verifies exact references before selection; fixture and E2E preserve regression coverage.

2

Capacity refresh destroyed the job card under interaction.

Concurrent Playwright journeys exposed unstable Angular tracking when canonical identity appeared after refresh. Stable provider-job identity changed the same workload from 0/25 to 25/25.

3

Google location did not fit the direct postcode design.

Provider-specific concepts risked leaking into persisted profiles. Location Service was extracted so canonical place/route semantics remain independent of Google and Postcodes.io.

4

Compact fixture profiles hid realistic selection pressure.

A rich profile exposed omitted and poorly prioritised evidence. Purpose-specific snapshots and relevance selection now preserve traceable inputs without making real personal data a test dependency.

5

Selected-output recovery assumed both document types existed.

CV-only and letter-only journeys exposed an old paired-output assumption. Operation state and UI now preserve truthful partial success and deliberate omission.

6

Provider dates, IDs and offsets did not share one meaning.

Compatibility normalisation was added at provider/domain boundaries while source attribution and original references remain visible for detail and application history.

Each fix added regression protection at the lowest useful layer and, where user behaviour mattered, at browser/E2E level.
Defect-driven engineering · 135
Major defects and design gaps · II

Failures that changed recovery, quality or boundaries

7

External-call deadlines did not align with durable operation deadlines.

A longer provider allowance alone was insufficient. Gateway bounds, caller read deadlines and persisted absolute deadlines were aligned; ambiguous outcomes enter reconciliation before retry.

8

One harmless structural defect could discard a whole document operation.

A narrowly scoped exact-duplicate repair was introduced, followed by the same structural and evidence validation. Semantic rewriting remains prohibited.

9

Professional export quality regressed under rich content.

Visual review found weak hierarchy and pagination that unit assertions could not express. A4 flow, spacing and page-break controls were corrected and retained as renderer tests.

10

Contract/client drift recurred across independently versioned services.

Producer OpenAPI, reviewed revisions and checksums, regenerated clients and semantic policy gates replaced copied binaries and undocumented assumptions.

11

Repository health could disagree with product readiness.

A service returning 200 was not enough. Mode checks, named-state verification, persistent-user journeys and focused cross-owner assertions were added to distinguish liveness from useful behaviour.

12

A capability could look ready before its complete user path was ready.

Payment backend/BFF wiring and live Stripe availability are now described separately from the unfinished purchasing interface and standard fixture-mode configuration.

Maturity signal. The important result is not that defects existed; it is that realistic evidence identified why earlier tests missed them and converted them into architecture and regression controls.
