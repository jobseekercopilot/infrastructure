Executive overview

One workspace for the fragmented work of finding a job

Job Seeker Copilot helps a candidate organise evidence, discover vacancies, prepare grounded application documents, track progress and review activity without repeatedly rebuilding the same context.

The product goal is not “AI writes a CV”. It is a traceable workflow from verified career evidence and a real vacancy to an application-specific document set.

The current software is a controlled private beta. Its normal local environment can use live Reed, Adzuna, JSearch, NHS Jobs, Find an apprenticeship, Postcodes.io, Google Maps and OpenAI paths. The default engineering environment remains deterministic, and live Stripe checkout is not enabled.

Bernard conceived the product, set its architecture and product direction, coordinated a multi-repository implementation, integrated the service boundaries, ran realistic acceptance work and repeatedly debugged failures exposed by real-user journeys.

Problem

Job search information is scattered across boards, CV files, notes and application trackers. Generic AI output can introduce unsupported claims.

Product response

Structured candidate evidence, provider-normalised vacancies, durable workflows, exact document versions and application tracking in one authenticated interface.

Engineering response

Domain-aligned services, producer-owned contracts, deterministic provider modes, fail-closed validation and recovery designed around unreliable external systems.

System architecture

Decomposed by ownership, not by repository count

Why gateways?

Browser gateways constrain routes and identity. Provider gateways isolate external credentials, DTOs and failure translation.

Why separate state?

Each persistent domain owns its PostgreSQL schema. Cross-service workflows use operation records and idempotency rather than shared tables.

Why fixtures?

The same boundaries can run with governed System Data responses, keeping CI repeatable and preventing accidental spend.

Backend and microservice design

Representative services and their decisions

Job Service

Bounds provider fan-out, maps adverts into a canonical model, retains field/source provenance, deduplicates related adverts and persists only explicit saved-job snapshots.

User Profile Service

Owns subject-scoped career data, search preferences, revisioned evidence and purpose-bound immutable snapshots used by generation.

Document Generation Gateway

Coordinates saved-job resolution, evidence snapshots, AI-credit reservation, drafts, approval, export and Tracker linkage through a durable PostgreSQL operation ledger.

Document Store

Owns families, immutable versions, current/approved pointers, lineage, file metadata and bytes. Local uploads cross an isolated ClamAV scan boundary.

Application Tracker

Owns lifecycle and immutable events. It independently verifies document ownership and commits exact version references atomically.

Reporting

Builds read-only summaries, recent activity, an indicative time estimate and an evidence export from owner-scoped upstream data.

AI document generation

Engineering around an unreliable model

Untrusted output

The model response is parsed against a strict schema, bounded, repaired only for harmless structure, and checked again against approved fact IDs.

Safe recovery

Retry is bounded to classified safe failures. Unknown outcomes are reconciled before another paid call. Retained responses can be replayed without calling the model again.

Fail useful

When acceptable model CV content cannot be obtained, an evidence-based deterministic CV can complete the workflow without invented qualifications or metrics.

Realistic testing changed the product

1

Document/application association.

A completed generation was not enough; exact retained versions also had to become visible and selectable on the correct application.

2

LLM duplicate and timeout behaviour.

Fail-closed validation evolved into narrow structural repair, bounded retry, outcome reconciliation, quarantine replay and fallback.

3

Rich real profiles.

Real career structure exposed selection and formatting assumptions that compact deterministic profiles did not.

4

Provider detail inconsistency.

Canonicalisation and source attribution matter because provider IDs, dates, descriptions and locations vary.

What the numbers do not prove: universal provider uptime, a complete manual accessibility audit, public production security, employment outcomes or 50-user capacity.

Data integrity, privacy and safety

Controls follow the data—not a compliance slogan

Trusted identity

Browser tokens remain in HttpOnly cookies. BFF route allowlists and CSRF checks constrain browser actions; service owners derive identity from validated subjects and dedicated service tokens.

Immutable lineage

Evidence revisions, saved-job snapshots, claims, document versions and application selections carry stable IDs/digests so later edits do not rewrite history.

Secret and personal-data boundary

Provider credentials are runtime-only. Real candidate data, CVs, cookies and passwords are excluded from fixtures, logs, screenshots and Git history.

Untrusted content

Provider text renders as text, external links pass an allowlist, uploads are bounded and scanned, and model output must satisfy schema and evidence policy.

Wallet safety

Reservations, stable operation keys, idempotent commit/release and unknown-outcome checks prevent an ordinary retry becoming a second charge.

Provider minimisation

Google DTOs and keys stay in one gateway; location labels/routes remain transient and attributed. Postcodes.io supplies persistable UK fields.

Scope boundary. These are implemented design controls, not a claim of certification, complete penetration testing, formal regulatory compliance or production-grade operational security.

Shareable-asset review

  • No API keys, tokens, cookies, passwords or private environment values.
  • No real CV, personal email address or phone number embedded in this dossier.
  • Application screenshots exclude account identity/contact information.
  • Private repositories are described, not linked as if publicly accessible.

Engineering challenges and lessons

Failures became architecture

1

LLM output could be fluent and still structurally or factually wrong.

The response: strict typed output, a claim ledger, exact evidence paths, narrow repair, fail-closed grounding, retained-response replay and deterministic CV fallback.

2

Multiple job sources describe the same opportunity differently.

The response: provider adapters, canonical source references, field provenance, URL/content deduplication and partial-provider status instead of a false all-or-nothing success.

3

A generated file is not the same as an application decision.

The response: immutable families/versions, explicit approval/current pointers and exact application selections owned by separate services.

4

Independent repositories create contract drift risk.

The response: producer-owned OpenAPI, reviewed revision/checksum pins, reproducible generated clients and semantic compatibility gates.

5

Deterministic tests overstated confidence in realistic use.

The response: retain canonical personas for repeatability, then add rich-profile, real-provider, paid-LLM and restart-persistence checkpoints with explicit cost authority.

6

Persistent manual state and fixture state have different needs.

The response: named fixture environments for engineering and a separately protected persistent real-user environment that survives ordinary restarts.

Mature engineering confidence is not “nothing failed”. It is knowing what failed, why the previous tests missed it, and what design now makes the failure safer.
